# 개념 업데이트 — 일괄 흐름 (references/batch.md, 전체 일괄 정의)

이 파일은 `conceptpowers:update-concepts`에서 사용자가 일괄 모드를 골랐을 때(계기 B) 필요할 때 읽히며, 후보
추출 규칙은 계기 A의 `newMaterial`에도 다시 쓰인다. 이 파일 옆 `define.md`의 단일 흐름 단계·품질 자가점검·상태
규칙은 여기서 정의하는 모든 개념에 그대로 적용된다.

## 일괄 흐름 (전체 일괄 정의)

개념의 주인은 사람(human-owns-contract)이라는 원칙은 그대로다: AI는 초안을 쓰고 묻고, 사용자가 확정한다.
일괄 모드는 대화를 체크포인트 두 번으로 줄일 뿐 없애지 않는다.

**자격 기준 관문도 그대로 적용된다** (`define.md`의 「자격 기준 관문」 절, 개념 `concept-scope`).
일괄 정의는 **후보를 많이 모으는 것**이지 후보를 전부 개념으로 만드는 것이 아니다 — 관문을
통과하지 못한 후보는 기능 명세나 상위 기준 문서로 내려가고, 그 판정은 checkpoint 1에서
사용자가 확인한다.

1. **후보 모으기** — 아래 출처를 **하나도 빠뜨리지 않고** 모두 쓴다(출처 하나로만 만든 목록은 불완전하다):
   - **`reference/` 문서**: 용어집 용어, 도메인 규칙, 명세된 동작.
   - **코드의 화면 접점 (필수)**: 내비게이션 메뉴, 라우트·페이지, 모든 버튼·폼 제출·메뉴 동작을 훑는다.
     화면 접점은 **빠짐없이 훑되**, 접점 하나가 곧 개념 하나가 되지는
     않는다 — 접점에서 **그 접점이 사용자에게 하는 약속**을 뽑아 후보로 올린다
     (예: "주문 취소 버튼" → *취소 가능 시점*이라는 약속, "관리자 메뉴" → *권한별 노출*이라는 약속).
     여러 접점이 같은 약속을 실현하면 **후보 한 줄로 묶는다** — 그것이 자격 기준의 "목적이 같으면
     새로 만들지 않고 넓힌다"이다. 약속이 안 나오고 생김새·배치·글자 표기만 남는 접점은
     개념 후보가 아니라 **기능 명세** 후보로 표시한다. 이는 init strict 전체 스캔의 기능 나열과 같은 방식이다 —
     참고자료에 한 번도 나오지 않는 화면·동작에도 드러낼 만한 의도가 있다. 다만 그 의도가 약속인지 방법인지는
     관문이 가른다.
   - **코드의 도메인 로직**: 검증 규칙, 권한 검사, 상태 전이, 식별자에 박힌 용어.
     합친 결과를 번호 붙은 후보 목록으로 보인다 — 한 줄에 하나씩
     ("결제 불변성 — 결제 후 가격·수량 변경 금지", …), 출처(참고자료 / 화면 접점 / 코드 로직)를 표시한다.
2. **자격 기준 관문 일괄 적용**: 모은 후보를 `define.md`의 「자격 기준 관문」 여섯 물음에 차례로
   걸어, 각 후보를 **개념 후보 / 기능 명세 / 상위 기준 문서 / 기존 개념으로 흡수** 중 하나로
   분류한다. 목적이 같은 후보끼리는 이 단계에서 한 줄로 합친다. 판정과 근거(어느 물음에서
   막혔는지)를 후보 줄에 적어 둔다 — 조용히 지우지 않는다. **기존 개념으로 흡수**한 후보는 이 일괄 흐름에서
   저장하지 않고, 사용자가 고르면 `references/edit.md`(`edit-concept --reason`)로 그 개념을 넓힌다.
3. **범위 확정 (checkpoint 1)**: 어느 후보로 진행할지 묻는다. **관문을 통과한
   개념 후보와 탈락 후보(어디로 내려가는지 포함)를 함께 보여주고**, 판정을 사용자가 뒤집을 수
   있게 한다 — 경계에 걸친 것은 사람이 정한다. 선택지에는 개별 후보 다중 선택과 함께
   **"전체 (모든 후보 정의)"가 반드시 첫 번째 선택지로** 있어야 한다 — 항목을 하나하나 체크하게 만들지 않는다.
   목록이 놓친 후보를 자유롭게 더할 수도 있게 한다.
4. **고른 후보 모두 초안 쓰기**: 고른 후보마다 초안을 쓴다 — 쉬운 말을 먼저, 기술 용어는 괄호 속 도움말로만 —
   그리고 **한꺼번에** 보여 검토받는다.
   깊이는 무게를 따른다: 약속이 넓은 개념은 definition·analogy·allow/restrict·immutable rules를
   모두 채우고, 약속이 좁은 개념은 짧아도 된다(아래 참고) — 짧은 정의와 판별 가능한 규칙 한두 개면
   게으른 초안이 아니라 완전한 초안이다.
5. **일괄 리뷰 (checkpoint 2)**: 사용자가 초안마다 확정 / 수정 / 버림을 정한다.
   - **확정된 새 개념** 초안 → 개념마다 단일 흐름 5-9단계를 이어간다(품질 자가점검은 초안 단계에서 이미 했다.
     정합성 검사는 묶음 전체에 한 번 돌리고, 개념마다 증빙을 남긴 뒤 `green`으로 올린다).
   - **남기되 지금은 검토하지 않을** 초안 → `pending`으로 둔다(사람이 쓴 초안은
     노랑으로 태어난다 — 개념 `settled-status`). `red`는 전수 스캔이 **자동 추론**한 제안 전용이니
     사람이 쓴 초안에 붙이지 않는다. 정합성 검사를 통과하고 사용자가 확인하면 그때 green으로
     정착시킨다.
   - 버린 초안 → 저장하지 않는다.
6. 저장한 개념마다 기능 명세(단일 흐름 step 1)와 `@concept` 태그를 잇고, 마지막에 뷰어를 한 번 다시 만든다:
   `node "<cli>" render --root .`
   관문에서 **기능 명세로 내려간 후보**도 이때 함께 기록한다 (`conceptpowers:scan`의 기능 명세 기록) —
   개념이 되지 못했다고 지식 지도에서 사라지면 안 된다. **상위 기준 문서로 내려간 후보**는
   `architecture.md` / `infra.md`에 한 줄로 남기자고 사용자에게 제안한다(기준선 수정이므로
   저장은 `update-concepts`의 계기 C로, 사용자 승인 아래에서만).

### 화면 접점에서 나온 개념 (짧아도 되지만, 약속이어야 한다)

화면 접점에서 뽑은 개념은 **짧아도 완전할 수 있다**. 다만 짧다는 것과 접점 하나마다 하나씩
만든다는 것은 다르다 — 개념이 되는 것은 버튼이 아니라 **그 버튼이 지키는 약속**이다.

- 통과 예: "관리자 메뉴는 관리자 권한이 있는 사용자에게만 보인다" → *권한별 노출*이라는 약속.
  같은 약속을 지키는 다른 메뉴·버튼이 열 개여도 개념은 하나다.
- 통과 예: "주문 취소 버튼은 배송 시작 전 주문에서만 활성화된다" → *취소 가능 시점*이라는 약속.
- 탈락 예: "취소 버튼은 오른쪽 아래에 회색으로 놓는다" → 생김새·배치라 상위 기준 문서로.
- 탈락 예: "메뉴 목록은 한 번 읽어 캐시해 둔다" → 약속을 지키는 방법이라 상위 기준 문서로.

통과한 개념을 적을 때:

- `description.definition`: 한두 문장 — 이 약속이 사용자에게 무엇을 보장하는가.
- 규칙: **판별 가능한 한 줄이면 품질 최소치를 넘긴다** — 노출 조건 / 활성 조건 / 동작 보장 중 하나.
- 안 맞는 칸(analogy, vision, lifecycle)은 비워 둔다 — 선택 항목이 비는 것은 정상이다.
- category는 보통 `feature` (+ 누가 보고 쓸 수 있는지에 대한 규칙이면 `permission`).

접점을 조용히 흘려보내지 않는다 — 개념이 안 되면 **어디로 갔는지**(기능 명세 / 상위 기준 문서 /
기존 개념으로 흡수) 후보 줄에 남기고 checkpoint에서 사용자가 확인하게 한다.

## 자동 추론 모드 (init strict 전체 스캔 전용)

`conceptpowers:init`의 전체 스캔(strict)이 부를 때만 쓰는 변형이다. 사람이 고르는 두 checkpoint를 건너뛰는 대신,
결과는 **미승인 제안(🔴 red)으로만** 저장된다. 개념 `human-owns-contract`대로 red 제안은 **규칙이 아니다** —
사용자가 승인(update-concepts 계기 D)해야만 개념의 규칙이 되고, 승인 전에는 코드를 다스리지 않는다. 그래서 AI가
규칙을 스스로 만들어 저장하는 것이 아니다. 사용자가 직접 고른 일괄 정의에는 쓰지 않는다.

1. 위 step 1(후보 모으기)을 그대로 한다 — **`reference/` 문서와 `reference/paths.md`의 바깥 자료도 빠짐없이**
   후보 출처로 쓴다. 자동 추론이라고 참고자료 확인을 건너뛰지 않는다(개념 `reference-first-duty`).
2. step 2(자격 기준 관문)를 그대로 한다. 판정과 근거는 후보 줄에 남긴다.
3. 관문을 통과한 새 후보만 초안을 쓰고 `define.md`의 품질 자가점검을 거쳐 `status: red`로 저장한다(define.md
   step 8). 근거(`sources`)에 참고자료 좌표를 남긴다.
4. **기존 개념으로 흡수**된 후보는 기존 개념을 고치지 않는다 — 그 slug를 기능 명세의 `concepts`에 적기만 한다.
   기존 개념을 넓혀야 할 것 같으면 보고 목록에 남겨 사용자가 나중에 계기 C로 정한다.
5. 관문에서 막힌 후보(기능 명세 / 상위 기준 문서)와 저장한 red 목록을 함께 보고한다. green 승격은 사용자가
   검토 후 승인을 요청할 때 계기 D로만 한다.
