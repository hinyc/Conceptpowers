# Conceptpowers: Init

이 프로젝트에 개념 기반 거버넌스를 켠다(선택 사항, D3/D15).

사용자에게는 사용자의 언어로 말한다. 출력 언어(`locale`)는 4단계 전까지 정해지지 않으며, 아래 따옴표 안 안내
문구는 사용자의 언어로 옮겨 쓰는 틀이다.

## 단계

1. 보충(backfill) 방식을 사용자와 확정한다(기본: incremental) — 9단계에서 지금 전체 스캔을 돌릴지만 정하며, CLI에 넘기지 않는다:
   - **incremental**(기본): 스캐폴드 + 마커만. 빠진 개념은 감사(audit)를 통해 점진적으로 보충한다.
   - **strict(전체 스캔)**: 프로젝트 전체를 스캔해 즉시 전부 보충한다.
     > ⚠️ **전체 스캔은 시간과 토큰이 많이 든다.** UI의 모든 버튼·동작과 화면 내용을 훑어 기능을 나열한 뒤,
     > 그 기능들이 하는 **약속** 가운데 기존 개념이 다루지 않는 것마다 개념을 추론한다(개념 하나가 여러 기능을
     > 맡을 수 있다). 중간 단계이거나 큰 프로젝트에서는 오래 걸리고 토큰을 많이 쓸 수 있다. 사용자가 한 번에
     > 전부 보충하기를 명시적으로 원하지 않으면 incremental을 권한다. strict를 돌리기 전에 항상 이 비용을 알린다.
2. 커밋 게이트 강도를 사용자와 확정한다(기본: standard):
   - **strict**: "개념과 어긋난 커밋을 차단합니다. 진행하려면 개념을 먼저 수정하고 충돌이
     없어야 합니다. 장기 운영·다인 협업·개념 우선 원칙을 강하게 지킬 프로젝트에 권합니다."
   - **standard**(기본): "문제를 보여주고 '그래도 진행할까요?'라고 묻습니다. 대부분의
     프로젝트에 알맞습니다."
   - **light**: "커밋을 멈추지 않고 경고만 모아 보고합니다. 소규모·단기·실험 프로젝트의
     도입 장벽을 낮춥니다. 나중에 standard/strict로 올릴 수 있습니다(init.json의
     `enforcement`를 직접 수정)."
     고른 값은 `--enforcement <strict|standard|light>`로 넘긴다.
3. 출력 언어를 사용자와 확정하고 `--lang`으로 넘긴다(`ko` 또는 `en`, 기본 `en`).
   이 값이 `init.json`의 `locale`이 되고, 이후 에이전트는 개념 내용, architecture/infra 문서, 사용자에게 보이는
   안내를 그 언어로 쓴다.
4. CLI로 스캐폴드한다(CLI 경로는 `CONCEPTPOWERS-ACTIVE` 세션 컨텍스트 또는 플러그인 dist):
   `node "<cli>" init --root . --lang <ko|en> --enforcement <strict|standard|light>`
5. 결과를 사용자에게 보고한다: `docs/conceptpowers/` 아래 다섯 요소(init/features/concepts/architecture/infra).
6. **architecture.md / infra.md를 채우도록 안내한다**(개념의 상위 기준).
7. **참고자료 경로를 묻는다(건너뛸 수 있음).** "개념을 작성할 때 참고할 문서 폴더나 파일이
   있나요? 경로를 알려주시면 등록해 두겠습니다 (여러 개 가능 — 건너뛰어도 됩니다).
   저장소 밖 자료는 절대 경로로(홈 아래면 `~/…`), 저장소 안 자료는 저장소 루트 기준
   상대 경로로 알려주세요."
   - 사용자가 경로를 주면: `node "<cli>" reference-add "<path1>" "<path2>" --root .` 후
     `added`/`skipped`를 보고하고 **`external[].status`가 `ok`가 아닌 것을 경고한다** — `missing`
     (경로 없음) 또는 `empty`(경로는 있으나 참고할 자료가 없음).
   - 사용자가 건너뛰면: `/conceptpowers:update-concepts`(참고자료 경로 등록)로 언제든 경로를 등록할 수 있고,
     `docs/conceptpowers/reference/paths.md`에 한 줄에 하나씩 경로를 적어도 되며, 자료를
     `docs/conceptpowers/reference/`에 바로 넣어도 된다고 한 번만 알린다. 다시 묻지 않는다.
   - 전체 흐름은 `/conceptpowers:update-concepts`의 계기 E(참고자료 경로 등록) 흐름을 본다.
8. **바로 다음 단계로 update-concepts를 제안한다.** 한 줄로 설명한다 — "update-concepts는
   프로젝트의 규칙과 의도(예: '결제 후 가격은 불변')를 기계가 검사할 수 있는 계약(개념)으로
   작성하는 단계입니다. 참고자료를 reference/에 넣어두거나 `reference/paths.md`에 외부 로컬
   경로(여러 개 가능)를 등록해두면 그 자료를 근거로 개념을 함께 작성합니다." — 그리고
   **지금 바로 `/conceptpowers:update-concepts`(계기 B — 새 개념 정의)로 이어갈지 묻는다.** 그렇다고 할 때만
   진행하고, 거절하면 언제든 쓸 수 있다고 알린다.
9. strict(전체 스캔)이면: 아래 **전체 스캔 절차**를 돌린 뒤 `conceptpowers:scan`으로 이어간다.

## 전체 스캔 절차 (strict)

시간·토큰 비용을 사용자에게 경고한 뒤에만 돌린다. 목표: **개념 · 기능 · 코드** 지식 지도 전체를 만든다 —
기능을 나열하고, 개념을 추론하고, 세 링크를 모두 이어 `#/graph` 화면이 연결되게 한다.

1. **동작으로 기능 나열**: 먼저 코드베이스에서 실행 가능한 접점을 모두 찾는다 — 버튼, 폼 제출, 메뉴 동작,
   라우트 핸들러, 명령 — 그리고 각각의 단순한 기능을 적는다.
2. **화면으로 기능 나열**: 각 화면/뷰가 무엇을 그리는지 분석해 사용자에게 드러나는 기능을 나열한다. 1단계와
   합쳐 중복 없는 기능 목록을 만든다.
3. **기능마다 기록하고 코드에 잇기**: 기능마다 구현 `codePaths`를 채운 기능 명세를 쓴다(_기능 → 코드_ 링크) —
   `conceptpowers:scan`의 「기능 명세 기록」 절차로.
4. **개념을 추론하고 기능을 잇기**: `conceptpowers:update-concepts`의 **자동 추론 모드**(그 일괄 절차)를 돌린다 —
   참고자료도 읽고 「자격 기준 관문」을 적용하며, 새 개념은 모두 `status: red`로 저장한다 — 규칙이 아니라 미승인
   제안이다: 개념 `human-owns-contract`대로 사용자가 승인한 뒤에야 규칙이 되고, 그 전에는 어떤 코드도 다스리지
   않는다. 기능은 접점마다 하나씩이지만 **개념은 접점마다 하나가 아니다** — 여러 기능이 한 개념을
   가리키는 것이 정상이다. 그런 다음 각 개념 slug(새것이든 기존 것이든)를 맞는 기능의 `concepts`에 적는다
   (_기능 → 개념_ 링크). 관문을 통과하지 못한 후보는 기능 명세나 `architecture.md` / `infra.md`에 대한 한 줄
   제안으로 간다.
5. **모든 코드 파일에 태그 달기(개념 → 코드, 빈틈 없이)**: 구현 파일에 `@concept:<slug>` 태그를 단다.
   **다스려지는 코드 파일은 모두 첫머리에 명시적 마커를 가져야 한다** — 어떤 개념도 해당하지 않는 파일
   (utils/types/config/scripts, 여러 기능이 함께 쓰는 공통 UI — 버튼·모달·레이아웃·디자인 시스템 컴포넌트 — 등)은
   태그 없이 두지 말고 **`@concept:none`**을 명시한다. 그런 다음 `conceptpowers:scan`의 「태그 규칙과 매핑 갱신」
   단계(`node "<cli>" map ...`)를 돌려 개념과 기능이 같은 파일에서 만나게 한다. (`none`은 예약 마커다: 게이트는
   통과하지만 진짜 개념은 아니다. `ignoreGlobs`는 재생성물·외부 코드만 자동 제외한다 — `dist/**`,
   `**/*.generated.*` 등. 그런 개념 없는 파일이 한 폴더에 모여 있으면 — 예: 공통 UI 키트 — 파일마다 태그를 다는
   대신 `init.json`의 `noConceptGlobs`에 개념 없음 영역으로 한 번에 정하자고 사용자에게 제안한다. 그 파일은 사용자가
   고친다.)
6. **다시 그리고 보고**: `node "<cli>" render --root .` 후 기능 목록 + 추론한 (red) 개념 + 이어진 지도를 보고하고,
   red 개념을 검토·승인하라고 사용자에게 알린다.

## 메모

- 이후 `docs/conceptpowers/`는 **읽기 전용 기준선**이다. 사용자가 명시적으로 요청할 때 `update-concepts`로만 고친다.
- **참고자료 원칙**: `reference/`는 개념을 작성·업그레이드할 때(`update-concepts`)만 읽는다. 검증 스킬
  (`review`, `scan`)은 개념 규칙만으로 판정한다.
- 언어는 나중에 `init.json`의 `locale`을 고쳐 바꿀 수 있다.
- `init.json`이 이미 있으면 덮어쓰지 않는다(사용자 설정 보존).
- 개념 `status`(세 상태 모델):
  - `green` — 정착된 계약: 사용자가 쓰고, 정합성 검사를 거치고, 사용자가 확인한 것. 지금 코드가 이미 따른다는
    뜻이 아니라 무엇이 지켜져야 하는지를 말한다.
  - `pending` — 사용자가 쓴 초안. 정합성 검사를 통과하고 사용자가 확인하면 `green`으로 정착하고, 아니면 해결될
    때까지 pending에 머문다. `conceptpowers:update-concepts` 참고.
  - `red` — 자동 추론(전체 스캔)된 제안으로 사용자의 검토·승인을 기다린다.
    `conceptpowers:update-concepts`의 승인 흐름(D) 참고.
