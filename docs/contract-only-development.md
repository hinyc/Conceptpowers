# 계약만으로 충분한가 — 스펙 없는 CDD와 판례법식 개념 진화

`concepts-vs-specs.md`가 "개념은 스펙이 아니다(판정 계약 vs 생성 계약)"라는 범주 구분을 다뤘다면,
이 문서는 그 다음 질문을 다룬다: **스펙을 아예 없애고, 개념의 계약(입출력 규약 + 의무 + 금지)만으로
개발을 이끌 수 있는가?** 그리고 그 방식이 대형·장기 프로젝트에서 마주치게 될 문제는 무엇인가.

이 문서는 2026-08 논의의 기록이다. 결론부터: **성립한다.** 단, 성립 조건과 장기 운영에서의
함정 두 가지를 알고 시작해야 한다.

## 1. 논제 — 순수함수 관점

주장은 이렇다:

> 입력·출력과 규약(의무 행동 + 부정 제약)만 명시하면, 구현 내용은 중요하지 않다.
> 순수함수처럼, 계약을 만족하는 구현은 내용 불문 전부 옳다. 삭제 기능이 의무 목록에
> 있으면 만드는 것이고, 없으면 안 만들어도 문제가 없다 — 그게 개념이니까.

이것은 design-by-contract를 끝까지 밀어붙인 관점이며, 논리적으로 일관된다.
계약 밖의 기대는 애초에 요구사항이 아니었던 것으로 취급한다.

### 성립 조건 1 — allow는 허가가 아니라 의무로 읽는다

부정 제약(restrict / immutableRules)만으로는 퇴화 해가 통과한다: "관리자는 하드 삭제되지
않는다"는 규칙은 삭제 기능을 아예 안 만든 코드도, 아무것도 안 하는 함수도 만족한다.
제약은 **가능한 것들의 영역**을 정의할 뿐 그 안의 **어느 점을 원하는지**는 말하지 않는다.

이 구멍은 `actions.allow`를 "해도 되는 것"이 아니라 **"반드시 할 수 있어야 하는 것"(의무
목록)**으로 읽는 순간 닫힌다. 의무 목록에 있으면 만들어야 하고, 없으면 안 만든 것이 정답이다.

### 성립 조건 2 — 입출력 규약은 개념이 아니라 테스트가 든다

개념 스키마(purpose / allow / restrict / immutableRules)는 산문 규칙용이지 타입 시그니처용이
아니다. I/O 규약을 개념에 정밀하게 적으려 들면 스펙 팽창(정밀도의 역설)이 다시 시작된다.
분업은 이렇다:

- **개념**: 의무(allow) + 금지(restrict / immutableRules) — "절대 Z는 안 된다"
- **테스트**(`conceptDrivenTests`): 입출력 규약 — "입력 X면 출력 Y"

개념 + 테스트가 계약의 전부이고, 그 계약을 만족하는 구현은 내용 불문 전부 옳다.
이때 "내용이 중요하지 않다"는 상태는 출발점이 아니라 **첫 생성 이후에 도달하는 상태**다.
첫 생성 때 계약은 성길 수밖에 없으며, 그것을 받아들이는 것이 이 방식의 전제다.

### 받아들여야 하는 규율 — 버그의 재정의

이 입장 아래서 "옳음"의 기준은 계약의 해상도만큼만 촘촘하다. 계약이 금지하지 않은 이상
동작은 버그가 아니라 **계약의 구멍**이다. 사용자가 이상하다고 느끼는 모든 것은
"코드 수정" 이벤트가 아니라 **"규칙 추가 → 재판정" 이벤트**가 된다. 스펙을 선불로 쓰는
대신 규칙을 후불로, 발견될 때마다 쌓는 지불 방식이며, 에이전트가 재생성을 싸게 해주는
환경에서는 합리적인 교환이다. 단, 팀 전체가 이 규율을 공유해야 굴러간다.

## 2. 개념의 진화 모델 — 판례법(common law)

개념은 사용하면서 점점 구체화된다:

1. 개념에 정의되지 않은 동작은 **자유구역** — 마음대로 구현해도 된다.
2. 어떤 기능이 필요해지면 의무 목록에 올려 **정식 개념으로 승격**한다.
3. 불편이나 충돌이 생기면 그 사건을 근거로 **제약에 명시**한다.

성문법(선불 스펙)은 시행 전에 모든 조항을 쓰려다 팽창해서 죽고, 판례법은 실제 사건이
생길 때마다 판례(규칙)가 쌓인다. 결정적 장점: **모든 규칙이 존재 이유를 갖고 태어난다.**
선불 스펙 조항의 상당수는 "혹시 몰라서" 쓴 추측이지만, 후불 규칙은 전부 실제 아픔에서
나온 것이라 낭비가 없다. `history.json` why-log가 규칙이 태어난 사건을 기록한다.

부수 효과로 **자유의 배분이 자동으로 이뤄진다**: 어린 기능 = 얇은 개념 = 넓은 자유 =
빠른 실험, 성숙한 기능 = 두꺼운 개념 = 좁은 자유 = 안정성. 탐색이 필요한 곳엔 자유가,
검증이 끝난 곳엔 규율이 저절로 가 있다. 선불 스펙은 첫날부터 모든 곳에 같은 무게의
규율을 걸기 때문에 이것을 하지 못한다.

이 진화 루프는 Conceptpowers의 상태 전이(🔴 red 추론 → 🟡 pending 제안 → 🟢 green 확정)가
제도화한 승격 절차와 정확히 일치한다. 즉 이 문서가 말하는 운영 방식은 도구에 이미 내장돼 있다.

## 3. 대형·장기 프로젝트에서의 함정 두 가지

이 절이 이 문서의 존재 이유다. 후불 계약 방식은 소형·단기 프로젝트에서는 함정이 드러나지
않지만, 규모와 기간이 커지면 반드시 다음 두 문제를 만난다.

### 함정 1 — 자유구역은 생각보다 자유롭지 않다 (Hyrum의 법칙)

개념에 정의되지 않은 동작이라도, 일단 코드로 존재하고 누군가 관측하면 **사실상의 계약**이
된다. 다른 코드가, 혹은 사용자가 그 우연한 동작에 의존하기 시작한다. 그래서 나중에
"불편해졌으니 제약에 명시"하는 순간, 그 제약이 이미 자라버린 자유구역 동작과 충돌하면
그것은 규칙 추가가 아니라 **파괴적 변경**이다.

후불 방식의 진짜 비용은 규칙을 쓰는 비용이 아니라, **늦게 쓴 규칙이 기존 의존성을 끊는
이주 비용**이다. 프로젝트가 크고 오래될수록 자유구역의 관측자가 많아지므로 이 비용은
기간·규모에 비례해 커진다. 피할 수 없으며, 받아들이고 시작하는 것이다 — drift 감지·재정렬
장치가 그 이주를 최소한 가시적으로 만들어 준다.

### 함정 2 — 규칙은 쌓이기만 하고 죽지 않는다 (개념 화석화)

사건이 생길 때마다 restrict가 하나씩 늘지만, 규칙을 지우는 사건은 자연발생하지 않는다.
수년이 지나면 태어난 이유가 이미 소멸한 규칙들이 서로 모순되며 개념을 화석화시킨다.
판례법이 상급심 판례 변경으로 낡은 판례를 폐기하듯, 여기도 **주기적 가지치기**가 필요하다.

- why-log가 있으므로 "이 규칙이 태어난 이유가 아직 유효한가"를 물을 수 있다.
- `check-consistency`가 규칙 간 모순을 표면화한다.
- 단, **가지치기를 트리거하는 것은 사람이다.** 에이전트는 green 규칙을 스스로 지우거나
  강등할 수 없다(상태 전이 가드). 장기 프로젝트라면 가지치기를 주기 행사(예: 분기별
  개념 감사)로 캘린더에 박아두는 것이 안전하다.

## 4. 요약 — 운영 지침

| 국면           | 지침                                                                                               |
| -------------- | -------------------------------------------------------------------------------------------------- |
| 첫 생성        | 한두 문단의 의도 + 얇은 개념(의무·금지)으로 시작. 계약이 성긴 것을 결함이 아니라 전제로 받아들인다 |
| 입출력 규약    | 개념이 아니라 테스트(`conceptDrivenTests`)에 둔다                                                  |
| 자유구역       | 개념에 없는 동작은 자유 — 단, 관측되는 순간 사실상의 계약이 됨(Hyrum)을 기억한다                   |
| 이상 동작 발견 | 코드 수정이 아니라 규칙 추가(pending) → 재판정 → 승격(green)의 루프로 처리한다                     |
| 늦은 제약 추가 | 파괴적 변경일 수 있음을 전제하고 이주 비용을 산정한다                                              |
| 장기 운영      | 주기적으로 why-log 기준 규칙 가지치기 — 트리거는 사람                                              |

한 줄 요약: **스펙은 소모품, 개념(계약)은 자산. 계약은 선불이 아니라 후불로 조여간다.
장기전에서 청구서는 두 곳에서 온다 — 자유구역에 자란 의존성(Hyrum)과 죽지 않는 규칙(화석화).**
