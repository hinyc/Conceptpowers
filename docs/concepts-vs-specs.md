# 개념은 스펙이 아니다 — 스펙 기반 개발이 깨지는 지점과 Conceptpowers의 응답

"코드를 신뢰성 있게 *생성*할 만큼 상세해진 스펙 문서는 결국 코드와 같은 크기·정밀도로 수렴한다" —
스펙 기반(agentic/spec-driven) 개발에 대한 널리 알려진 비판이고, **옳은 지적이다**.
Conceptpowers는 이 비판을 반박하는 도구가 아니라, 애초에 그 범주 밖에 있는 도구다.
이 문서는 그 범주 구분과, 스펙 문서가 실제로 깨지는 지점마다 Conceptpowers가 무엇을 다르게 하는지 정리한다.

## 1. 범주 구분 — 생성 계약 vs 판정 계약

스펙 문서의 실패는 대부분 문서에게 **생성(generate)** 역할을 맡길 때 생긴다: 문서만 읽고 동작하는
구현이 나와야 하니, 문서는 모든 분기·필드·알고리즘을 담을 때까지 정밀해져야 하고, 그 끝은 코드다.

Conceptpowers의 개념은 **판정(judge) 계약**이다. 근거는 검증의 비대칭성이다:

> "관리자는 하드 삭제되지 않는다" — 이 한 줄로 구현을 만들 수는 없다. 그러나 어떤 변경이
> 이 규칙을 **위반했는지는 판정할 수 있다.**

그래서 개념은 **의도적으로 불완전(incomplete by design)** 하다. *how*의 source of truth는 여전히
코드이고, 개념은 *왜*와 _절대 일어나면 안 되는 것_(purpose / allow / restrict / immutableRules)만
소유한다. 코드의 대체재가 아니라 코드 위에 얹히는 보완재이므로, "충분히 상세해질" 압력 자체가
존재하지 않고 코드로 수렴하지도 않는다.

이것은 스펙 문서 자체를 부정하는 게 아니다 — 부정하는 것은 스펙을 *생성 청사진*으로 쓰는 방식이다.
superpowers의 프로세스(아이디어 → 스펙 → 계획 → TDD)에서 스펙은 사람과 에이전트가 함께 다듬는
설계 대화의 산물이고, Conceptpowers는 그 아래에 판정 게이트를 더할 뿐이므로 서로 충돌하지 않는다.

## 2. 널리 지적되는 한계 5가지와 Conceptpowers의 응답

| 지적되는 한계                                                                                | Conceptpowers의 응답                                                                                                                                                                                                                                                         |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **"스펙이 코드보다 단순·저렴하다"는 전제** — 정밀한 스펙 작성은 코딩만큼(또는 그보다) 비싸다 | 그 전제를 채택하지 않는다. 계약은 코드를 대체하지 않고 위에 얹힌다. 사람이 쓰는 것은 분량은 작지만 가장 어려운 부분(불변 규칙)뿐이고, 코딩은 그대로 코딩이다                                                                                                                 |
| **정밀도를 올리면 문서가 구현 크기로 팽창**                                                  | 개념의 분량은 코드량이 아니라 **지켜야 할 규칙 수**에 비례한다. 경계 장치: `enforceScope`(리팩터·오타·포맷은 판정 범위 밖), `ignoreGlobs`(생성물·외부 코드 면제), quality floor(개념당 집행 가능 규칙 최소 1개), `@concept` 태그 링크(코드를 전면 미러링하지 않음)           |
| **문서로부터의 생성이 불안정** — 상세한 스펙조차 준수되는 구현을 보장하지 못한다             | 1회 생성의 성공에 기대지 않는다. 생성 신뢰성 문제를 **지속 검증** 문제로 바꾼다: 편집 전(`check-concept`) → 커밋 전(PreToolUse 게이트) → 커밋 후(PostToolUse 재정렬로 drift 자동 해소) → 상시(`audit`)의 4지점 반복 판정                                                     |
| **납기 압력 아래 문서는 slop이 된다** — "스펙처럼 생긴 문장 뭉치"                            | 자유 산문을 금지하는 스키마(purpose / allow / restrict / immutableRules)가 그 형태를 구조적으로 차단한다. 전체 정합성은 `check-consistency` 0충돌 요건이 담당하고, 에이전트가 추론한 개념은 🔴 red로 태어나 **사람이 승격하기 전까지 코드를 통치하지 못한다**                |
| **Garbage in, garbage out** — 흐릿한 입력을 에이전트가 메워주지 않는다                       | 동의한다 — 정화하지 못한다. 대신 **가시화하고 국소화한다**: 모호한 개념은 quality floor에서 걸리고, 판정 시점에 `reference/`로 도피하는 것이 금지돼 있어("개념이 모호해 판정 불가면 개념을 고쳐라") 모호함이 결함으로 표면화되며, 충돌은 🟡 pending으로 이유와 함께 기록된다 |

## 3. 덜 논의되지만 더 파괴적인 문제들

스펙 논쟁은 대개 "첫 생성"만 본다. 실제 비용은 그 다음 수백 번의 편집에서 난다.

1. **단방향성 — 스펙 부패.** 생성 이후 코드가 변할 때 문서를 되돌릴 장치가 없다.
   → alignment lock이 개념↔코드의 정렬 상태를 추적하고, 커밋 게이트가 drift를 잡고, 커밋 후 자동 재정렬로 신호가 스스로 청산된다.
2. **규칙 지역화 불가.** 긴 문서는 "이 파일을 고칠 때 어떤 조항이 적용되는가"에 답하지 못한다.
   → `@concept` 태그(source of truth) + 매핑 캐시 + concept·feature·code 지식 그래프.
3. **문서 내부의 자기모순.** 조항이 늘수록 서로 충돌하고 아무도 모른다.
   → `check-consistency`가 전 개념 교차 검사, green↔green 충돌은 사람에게 에스컬레이션.
4. **권위의 출처 불명.** 어느 조항이 사람이 확정한 것이고 어느 것이 AI 초안인지 구분이 없다.
   → 🟢 green / 🟡 pending / 🔴 red 3단 상태 + 엔진의 상태 전이 가드.
5. **변경 이유의 소실.** 조항이 바뀐 *이유*가 어디에도 남지 않는다.
   → `history.json` why-log가 이유를 기록하고, drift 경고에 그 이유가 함께 표시된다.
6. **세션·에이전트 간 컨텍스트 소실.** 새 세션의 에이전트는 왜 그렇게 돼 있는지 모른 채 시작한다.
   → SessionStart 훅이 활성 개념과 미해결 drift를 컨텍스트에 주입한다.
7. **테스트가 규칙이 아니라 구현을 고정.** 스펙 논쟁은 테스트를 거의 다루지 않는다.
   → `conceptDrivenTests`: 테스트 시나리오를 개념의 allow / restrict / immutableRules에서 도출한다.
8. **그린필드 전용이라는 한계.** 기존 코드베이스에는 애초에 스펙이 없다.
   → incremental backfill 기본값 + `audit` 전수 점검 + 선택적 `strict` 전수 스캔.

## 4. 해결하지 못하는 것

- **시간을 절약해 주지 않는다.** 개념은 속도 장치가 아니라 의도 보존 장치다.
- **형식 증명이 아니다.** 판정은 LLM의 추론이며, 엔진이 결정론적으로 보장하는 것은
  스키마 검증·상태 전이·매핑·drift 상태뿐이다.
- **attestation은 자기 신고다.** 검사를 *생략*한 채 숨기는 것은 막지만, 검사가 *철저*했음을 증명하지는 못한다.
- **비용은 실재한다.** `strict` init 전수 스캔은 큰 프로젝트에서 시간·토큰 부담이 크다.
- **게이트를 반복 강제 통과하면 보증은 무효다.** `[Drift Ignored]`가 누적되면 개념↔코드 정렬 보증은 사라진다.
