# redteam 스킬 설계

- 날짜: 2026-10-27
- 상태: 승인됨 · 구현됨 (2026-10-27, 브랜치 `feat/redteam-skill`) — auto 연결만 보류
- 스킬 이름: `redteam` → `/conceptpowers:redteam`, 한국어 호출어 "레드팀"

## 1. 의도와 이유

Claude Code의 `/code-review ultra`(여러 에이전트가 찾고, 다른 에이전트가 반박해 살아남은 것만 보고)를 벤치마킹하되,
Conceptpowers 개념을 기준으로 **비판적으로** 코드를 점검하는 스킬을 만든다.

기존 `review`는 "코드가 개념 규칙을 어기는가"만 가볍게 판정한다. 코드를 바꿀 때마다 안내되므로 싸야 하고, 보고만 하고 고치지 않는다.
사용자가 원하는 것은 그 이상이다:

- 긍정적으로만 보지 않고 **일부러 반대 입장에서** 약점·허점·더 나은 방법을 찾는다 (레드팀).
- **중복**을 찾아 지운다.
- 작업하다 **원래 목적에 맞지 않게 생긴 것**을 찾아 정리한다.
- 코드가 **과하지 않게, 필요한 기능만, 부작용 없이** 구현됐는지 본다.
- 이 모든 판단 내내 **목적을 확인하며 방향이 어긋나지 않게** 한다.

review와 겹치는 것은 "개념 준수 판정" 하나뿐이고, 호출 시점·비용·태도·범위·결과(수정까지 함)가 달라서 review를 키우지 않고
새 스킬로 분리했다 (사용자 결정: "결이 같으면 review 업데이트, 목적이 다르면 분리").

## 2. 목표 / 비목표 / 반목표

**목표**
- 개념 기준 + 작업 목적 기준으로 다섯 축을 점검한다: 개념 준수 · 레드팀 비판 · 중복 · 과잉·목적 이탈 · 부작용.
- 지적은 반박 검증을 거친 것만 보고한다.
- 사용자가 승인한 항목만 고친다.

**비목표**
- 개념을 쓰거나 고치는 일 (→ `update-concepts`).
- `@concept` 태그·매핑 정리, 표식 없는 코드 분류 (→ `scan`).
- 개념 최신화 자체 (→ `auto` / `update-concepts`). redteam은 최신 여부를 확인만 한다.

**반목표 (기술적으로 돌아가도 실패인 것)**
- redteam 자신이 review·scan·auto와 같은 일을 다시 구현해 중복을 만드는 것.
- 개념이 없는(`@concept:none`) 코드를 "개념이 요구하지 않으니 과잉"으로 잘못 몰아붙이는 것.
- 반박 검증 없이 지적을 쏟아내 오탐으로 사용자를 지치게 하는 것.
- 승인 없이 코드를 고치는 것, 또는 수정이 또 다른 과잉·목적 이탈을 만드는 것.

## 3. 제약

- **reference/는 읽지 않는다.** 판정 기준은 개념과 작업 목적뿐이다 (review와 같은 원칙).
- **개념을 스스로 고치지 않는다.** 개념 위반은 코드를 고칠지 개념을 바꿀지 사용자가 정하고, 개념 수정은 `update-concepts`(C)로 넘긴다.
- **개념 미지정은 정상이다.** `@concept:none` 표식과 `init.json`의 `noConceptGlobs`(개념 없음 영역)는 허용된 상태다.
- **스킬 표면 개념(`skill-surface`)을 따른다:** 스킬 이름 = 폴더 이름, 설명문은 한 줄이며 쌍점 뒤 공백(`": "`)을 넣지 않는다,
  가리키는 절차 문서·스킬·CLI 명령은 실제로 존재해야 한다, 긴 절차는 `references/`로 내리고 그 문서에는 스킬 머리말을 두지 않는다.
- **거버넌스 순서:** 이 저장소는 개념 거버넌스가 켜져 있다. 스킬을 추가하기 전에 이 스킬의 개념을 `update-concepts`로 정의하고,
  사용자 확인 아래 green으로 정착시킨 뒤 구현한다.
- Claude Code와 Codex 양쪽에 배포되는 플러그인이다.

## 4. 사용자가 정한 설계

### 4.1 실행 흐름 (세 모드 공통)

**0단계 — 개념 최신 확인 (필수, 읽기 전용)**
- `auto` Stage 0 진단과 같은 항목을 그대로 확인한다 (새로 만들지 않고 그 절차를 가리킨다):
  `reference-diff`(changed/removed/affected), 개념 status 분포(🔴 red / 🟡 pending), `audit`(깨진 태그·표식 없는 코드).
- 낡은 것이 있으면 멈추고 무엇이 낡았는지 보인 뒤 묻는다:
  (a) `auto` 또는 해당 스킬(`update-concepts`·`scan`)로 먼저 최신화 / (b) 그대로 진행 — 보고서에 "낡은 개념 기준으로 리뷰함" 표시.
- redteam이 `update-concepts`를 직접 돌리지 않는다 (reference를 읽고 사용자 확인 단계가 많은 스킬이라 섞으면 원칙이 깨진다).

**1단계 — 목적 고정**
- 두 가지 목적을 몇 줄로 정리해 사용자에게 보이고 확인받는다. 이후 모든 판단·수정은 이 기준에 비춘다.
  - 개념 쪽 목적: 대상 코드에 걸린 green 개념의 규칙(`actions.allow / restrict`, `principle.immutableRules`)과 목적(`purpose`).
  - 작업 쪽 목적: 이번 변경이 하려던 일 (출처는 모드별, 4.2).
- 도구로 못 잡는 "의도 자체가 바뀐 낡은 개념"은 사용자가 이 확인에서 짚는다.

**2단계 — 코드 분류**

| 코드 종류 | 개념 준수 | 과잉·목적 이탈 기준 | 중복·부작용·레드팀 |
|---|---|---|---|
| 개념 태그 있음 | review 판정 절차 재사용 | 그 개념이 요구하지 않는, **사용자에게 보이는** 동작·옵션·기능. 내부 보조 코드는 과잉으로 보지 않는다 | 모두 적용 |
| `@concept:none` / 개념 없음 영역 | 해당 없음 (정상) | 작업 목적에 비해 과한 것 — 안 쓰이는 export·옵션, 쓸데없는 추상화 | 모두 적용 |
| 표식 없음 | — | — | 판단하지 않고 목록만 → `scan`으로 넘김 |

- `none`인데 실제로는 사용자에게 하는 약속(규칙)을 담은 코드는 "none 오분류 후보"로 보고만 하고 `scan`/`update-concepts`로 넘긴다.

**3단계 — 축별 리뷰어 병렬 실행 (축 하나에 에이전트 하나, 총 5)**
1. 개념 준수 — review의 판정(위반 없음 / 위반 / 판단 불가) 그대로.
2. 레드팀 비판 — 반대 입장에서 약점·허점·더 나은 방법.
   - **기본:** 지적마다 근거를 개념 규칙이나 작업 목적에 묶는다. 묶을 수 없는 지적은 내지 않는다.
   - **선택:** 실행할 때마다 1단계(목적 고정) 확인과 함께 "레드팀 범위를 목적에 묶을지(기본), 일반 품질(보안·성능·가독성 등)까지
     넓힐지"를 **항상 묻는다**. 묻지 않고 기본으로 넘어가지 않는다. 넓히기를 고르면 이 지적들은 보고서에서
     "목적 밖 일반 품질"로 따로 묶어, 목적에 묶인 지적과 섞이지 않게 한다.
3. 중복 — 같은 일을 하는 코드·문서.
4. 과잉·목적 이탈 — 위 분류표 기준.
5. 부작용 — 의도하지 않은 동작 변화, 호출하는 쪽에 미치는 영향.

**4단계 — 반박 검증**
- 지적마다 별도 에이전트가 "문제가 아니다" 쪽으로 반박을 시도한다. 반박을 견딘 것만 남긴다.

**5단계 — 보고**
- 심각도순. 항목마다: 파일·위치 / 어느 축 / 근거(어느 개념 규칙인지, 또는 작업 목적의 어느 부분인지) / 제안 수정.
- 별도 목록: 판단 불가(개념 모호 → `update-concepts` F 권장), none 오분류 후보, 표식 없는 코드(→ `scan`), 표본 검사로 넘긴 파일, 0단계에서 낡음을 무시하고 진행했는지.

**6단계 — 승인 후 수정**
- 사용자가 고른 항목만 고친다.
- 고친 뒤 그 수정이 새 과잉·목적 이탈·중복을 만들지 않았는지 1단계 목적에 비춰 다시 확인한다.
- 개념 위반 항목은 (a) 코드 수정 (b) 개념 수정(`update-concepts` C) (c) 기능·개념 분리 중 사용자가 고른다.
- 코드를 고치면 `@concept` 태그·매핑도 함께 갱신한다 (review와 같음).

### 4.2 모드

| 모드 | 대상 | 작업 쪽 목적의 출처 | 비고 |
|---|---|---|---|
| ① 변경분 | 커밋 안 된 변경 + 기준점 이후 커밋. 기준점: main이 아닌 브랜치면 main에서 갈라진 지점, main 위면 마지막 릴리스 태그. 사용자가 범위를 주면 그것을 우선 | 커밋 메시지, 관련 기능 명세(`features/`), 사용자 설명 | 바뀐 파일을 호출하는 쪽까지 봐서 부작용을 잡는다 |
| ② 개념 하나 | 개념 slug 하나에 걸린 코드 전부 (review ②와 같은 찾기) | 그 개념 자체 | 개념 안의 중복·과잉을 깊게 |
| ③ 전체 | 모든 green 개념의 코드 + `none` 코드 | 각 개념, `none`은 쓰임새 | 시작 전 규모(파일 수)를 알리고, 많으면 표본 검사임을 밝힌다 |

- 모드를 말하지 않고 부르면 묻는다.

### 4.3 다른 스킬과의 관계

- `review`: 개념 준수 판정 절차를 가리켜 재사용한다. review는 바꾸지 않는다.
- `scan`: 표식 없는 코드·none 오분류 후보·태그 정리를 넘긴다.
- `auto`: 0단계가 auto Stage 0 진단 절차를 가리킨다.
- `update-concepts`: 개념 수정·판단 불가 업그레이드를 넘긴다.

## 5. 에이전트(Claude)가 정한 것 — 사용자 확인 필요

- 모드를 말하지 않았을 때 변경분이 있으면 ①을 먼저 권한다.
- `auto`의 마지막 단계(review) 뒤에 "레드팀까지 할까요?"를 선택지로 하나 붙인다 (강제 아님).
  - **보류 (2026-10-27):** 커밋 게이트가 막았다. main에서 고쳐진 `human-owns-contract`의 테스트 검토 기록이 아직
    없는데 `skills/auto/SKILL.md`가 그 개념에 걸려 있다. 사용자 결정으로 미뤘고, 그 개념이 정리되면 다시 붙인다.
- 서브에이전트 도구가 없는 환경(예: Codex 일부)에서는 같은 다섯 축과 반박 검증을 한 에이전트가 차례로 수행한다.
  이때 반박 단계는 지적을 쓴 직후가 아니라 축 리뷰를 모두 마친 뒤 따로 한다.
- 심각도는 세 단계로 한다: 높음(규칙 위반·부작용·데이터 손실 위험) / 중간(중복·과잉) / 낮음(개선 제안).
- **0단계 멈춤 범위:** 낡은 항목 중 **대상 코드나 그 코드에 걸린 개념에 닿는 것**이 있을 때만 멈추고, 나머지(다른 곳의 red/pending,
  범위 밖 표식 없는 코드)는 보고서에 적기만 한다. 걸러내기는 진단 결과 목록을 대상 파일·개념 slug로 거르는 것까지만 하고,
  진단 자체는 새로 만들지 않는다.
- **반박 검증 묶음:** 심각도 높음은 지적마다 반박 에이전트 하나, 중간·낮음은 축별로 묶어 반박 에이전트 하나가 처리한다.
  한 번 실행의 반박 에이전트는 최대 10개로 하고, 넘으면 심각도순으로 자르고 잘린 것은 "미검증"으로 보고한다.
- **기존 개념과 충돌:** 새 개념의 정합성 검사에서 기존 green 개념과 충돌하면 거기서 멈추고 사용자에게 묻는다.
  기존 개념 수정은 이번 작업에 자동으로 포함하지 않는다.
- **6단계 수정의 끝:**
  - 동작을 바꾸는 수정은 저장소 규칙대로 테스트를 먼저 쓴다(개념 기반 테스트 규칙 포함).
  - 커밋은 하지 않는다. 사용자가 직접 하거나 따로 요청한다.
  - 수정 뒤 재확인은 다섯 축을 다시 돌리지 않는다. 고친 파일에 대해 과잉·목적 이탈·중복 세 축만 가볍게 자체 확인한다.

## 6. 빌더에게 맡기는 것

- SKILL.md와 `references/` 사이의 절차 분량 배분 (스킬 표면 규칙 안에서).
- 각 리뷰어·반박 에이전트에게 줄 프롬프트 문구와 결과 형식.
- 이 스킬을 다스릴 개념의 이름·문구 (단, `update-concepts`로 정의하고 사용자 확인을 거친다). 기존 `skill-surface`의 `codeLinks`에 새 SKILL.md를 더하는 일 포함.
  - **빌더 판단:** `skill-surface`는 고치지 않았다. green 개념을 고치면 pending으로 내려가 재정착이 필요하다(5절
    "기존 개념 수정은 자동으로 포함하지 않는다"). 형식 검사 테스트는 모든 스킬 폴더를 훑고, 어긋남 판정은 매핑과
    기능 명세만 본다. 대가: 뷰어 그래프에서 redteam SKILL.md가 `skill-surface` 밑에 보이지 않는다.
- 설명문(트리거 문구) 구성 — "레드팀", "redteam", "비판적 검토", "중복 정리", "과잉 구현 점검" 같은 사용자 말을 담는다.
- README·README.ko.md, 플러그인 매니페스트, 기존 테스트(스킬 목록·참조 검사 등)에 필요한 반영.
